## 2. 方案总览（目标形态）

```
实时路（常规视图，暗图窗）
   │ 点击「增强窗/触发键」
   ▼
冻结（复用 HQ 的冻结/全屏语义，O90）
   ▼
取 1 帧（TH1 dmabuf，与 HQ 同源取得方式）
   ▼
板端 DCM 单帧链路：
   ① g_a + h_a（RKNN）→ 潜变量 y + 超先验 z
   ② 熵编码（CPU，真码流）→ 得 **真实字节数/码率**
   ③ 熵解码（CPU）→ ④ g_s（RKNN）→ 重建特征 x_hat
   ⑤ （可选）REC（RKNN）→ 重建像素图
   ⑥ 检测（板端轻量检测器 RKNN）→ 检测框
   ▼
全屏展示：**重建图 + 检测框 + 码率(bpp/kbps) + 档位**（仿 HQ 全屏）
   ▼
点击/超时退出（复用 `ui.fullscreen_timeout_ms` 语义）
```

> **退出语义的两处增补（事后登记）**：① **（2026-10-15 用户指示）** 超时兜底按视图区分 —— **DCM 结果屏**（`fullscreen_dcm`）**60 s**、**处理中**（`dcm_pending`）与 **HQ 全屏**仍 **30 s**（`main.DCM_DEMO_RESULT_TIMEOUT_MS = 60000`，**机制值、非 config 键**；主基准 §14 追加 55）。② **（2026-10-14 用户裁定）** 触发方式收窄 —— **DCM 演示只由底栏「DCM 特征检测」键触发**，HQ 键不再自动接 DCM（主基准 §3.5）。

**演示内容（✅ 已裁定，用户 2026-10-10）**：**只展示单臂 B —— 不做 A/B 对照**。即：把**我们的增强结果**送进 DCM，展示 **DCM 解码重建出的画面（= 机器实际"看到"的那一帧）**，叠加**检测框**，并标出**真实码率 / 档位**；**两屏显示同一画面**（沿用「HDMI 镜像 MIPI」现有契约 ⇒ **不新增显示分工**）。原「**同码率 A/B 对照**」建议**作废**（登记 = 主基准 §15 **O166**；详见 §6 第 4 项）。**档位固定 = 第 3 档**（`--quality 3` ⇒ `q_map_factor 0.265`）；**检测器 = YOLOX-s**（界面 / 讲解须如实标注"**板端轻量模型，非 DCM 规范检测器**"）（裁定 = §6 第 2 / 3 项）。**⚠️ 已订正（主基准 §14 追加 54，2026-10-14 用户裁定「按 Faster R-CNN 更新文档并订正基准」）：检测器实际实现 = DCM 规范检测器 Faster R-CNN（`faster_rcnn_X_101_32x8d_FPN_3x`，COCO 80 类；板上 NPU 跑 backbone+FPN / RPN 头 / box_head，CPU numpy 跑 anchor+decode+NMS / RoIAlign / 最终解码）⇒ 上文「检测器 = YOLOX-s」及「非 DCM 规范检测器」的免责标注义务**作废**；本段历史逐字保留。**

## 4. 关键技术风险与对策

| # | 风险 | 说明 | 对策 |
|---|---|---|---|
| R1 | **RKNN 算子不支持**（最高） | DTM 网络含 **RNAB/CAB/TAM 注意力、ResAU 分组卷积、GDN、PixelShuffle、高斯混合概率模型** | **S0 先证伪**；不支持时的退路 = 等价替换（**可能需重训**，成本剧增 ⇒ 届时应重新裁定）。**✅ 2026-10-10 更新：R1 已消除**（S0~S9 全过：10/10 网可导出 + 可转 RKNN + 板上可跑，见 §8.8~§8.17） |
| R2 | **量化精度损失** | 熵模型参数对量化敏感（ZDE++ 移植已有同类经验可循） | S1 对拍 + 必要时 FP16 档。**2026-10-10 更新：已按 FP16 落定**，一致性口径 = **接受**（见 §6 第 5 项），**新增机制性事实** = FP16 误差被 MCM 内 8 级级联 `round()` 放大（§8.17） |
| R3 | **熵编码需移植** | 主路径依赖 `models/entropy_models` + 高斯混合概率模型（torch 生态）；**rANS 是串行数据相关步骤，不能上 NPU** | 在 **CPU** 用 C++/纯 Python 重写**区间编码**；**必须产出真码流**（否则码率造假 ⇒ 违反 `10-evidence.md` §2 精神）。**2026-10-10 更新：已落定** —— 熵编码走 **DTM 自带 rANS C++ 源码**，板端编 aarch64 `.so`，**与 RM 逐字节一致**（§8.17） |
| R4 | **检测器降级** | DCM 规范检测器 = detectron2 Faster R-CNN（RPN/ROIAlign/NMS，**转 RKNN 很难**） | **⚠️ 已订正（主基准 §14 追加 54）**：实际走通了**混合架构**（NPU 跑 backbone+FPN / RPN 头 / box_head，CPU numpy 跑 anchor+decode+NMS / RoIAlign / 最终解码）⇒ **用的就是 DCM 规范检测器，本行「降级」不成立、「如实标注非规范检测器」义务作废**。以下为历史（原对策 = 换**板端轻量检测器 = YOLOX-s**（**Apache-2.0**；**已裁定 2026-10-10**，见 §6 第 2 项）；**界面/讲解须如实标注"检测器为板端轻量模型，非 DCM 规范检测器"**；**残留** = 0.7 Lux 增强帧上的实际检出率**未验证**（S3 实测）） |
| R5 | **与 DTM RM 非逐位一致** | 板端为**移植版**（**FP16 量化**；熵编码本身已与原版 rANS **逐字节一致**，见 R3） | 明确标注为"**板端移植版**"，**不得宣称与 DCM RM 一致**；如需对比，RM 结果另行离线产出（147）。**2026-10-10：一致性口径 = 接受**（见 §6 第 5 项） |
| R6 | **核与实时性冲突** | 演示占用 NPU；若**不冻结**实时链，则与 core0+1 冲突 | **沿用冻结语义**（实时链停）；不冻结方案不采纳 |

### 8.1 环境（本机实测）

| 项 | 实测 | 对照 DTM 要求 |
|---|---|---|
| Python | **3.8.10** | ✅ 与 DTM 要求（3.8）一致 |
| GPU | **RTX 3090 / 24 GB** | ✅ 与 DTM 开发环境同类 |
| torch | **2.0.1+cu117** | ⚠️ DTM 要求 **1.12.1+cu116**（大版本差异 ⇒ 权重加载/导出算子行为可能不同） |
| 缺包 | cv2 / einops / bitstring / torchac / pycocotools / timm / detectron2 / compressai / onnx / rknn-toolkit2 | 需安装（多数为轻量包；detectron2、compressai、rknn-toolkit2 较重） |
| 磁盘 | `/` 可用 **95 G** | ✅ |
| ⚠️ 沙箱 | 本机执行受 **TRAE 沙箱限制**（部分路径不可写） | **装包/建环境可能需在沙箱外执行** |

⇒ **离线步骤（S0/S1）的环境基本具备**；唯一硬缺口 = **装包 + torch 版本对齐**。

### 8.2 算子清点（已确定）

**关键结论：主链路不含任何注意力 / 矩阵乘 / Softmax。** 注意力类（`TAM`/`RNAB`/`CAB`、`LayerNorm`、`MatMul`、`Softmax`）**只存在于未被主链路实例化的分支**（`src/codec/components/autoencoder_data/` 的 `EncoderBasic` / `DecoderHigh`）。主链路算子面：

| 类 | 算子 | 备注 |
|---|---|---|
| 卷积 | `Conv2d` / **Grouped Conv（groups=64 / 128）** / **Depthwise 分离卷积** / `ConvTranspose2d`(4×4 s2) | 占绝对多数 |
| 逐元素 | Add / Mul / Div / Sub / Abs / Clamp / LeakyReLU / ReLU / Sigmoid（仅瓶颈） | 常规 |
| 形状 | `PixelShuffle` / `Concat` / `chunk`(split) / `reshape` / `view` / `stack` / `Pad(replicate)` | ⚠️ 见 §8.6 |
| **整数定点** | **int32 卷积 + `bitwise_right_shift` + 逐通道 shift**（`hyper_scale_decoder`） | ⚠️ 最高风险 |
| 应剥离 | `torch.erfc`（`GaussianConditional` / `GMProbModel`）、`torch.cumsum`（CDF 构建） | **整体移到 CPU**，不进 NPU 图 |

### 8.3 形状与动态性（960×544 输入，已确定）

`pad → 960×576`；特征 **128×144×240**（1/4）→ `y` **128×36×60**（1/16）→ `z` **128×9×15**；`h_s` 输出 256×36×60；`g_s` 回 128×144×240；`REC` 出 **3×576×960**。
**固定输入下全静态**（无数据相关分支/循环）⇒ **ONNX 导出无动态 shape 障碍**。

### 8.4 熵编码链（已确定）

- 主链路用 **compressai 的 rANS**（`models/entropy_models/entropy_models.py` 内 `ans.RansEncoder/RansDecoder` + C++ 扩展 `compressai._CXX.pmf_to_quantized_cdf`）；**不是 torchac**（torchac 仅 CLIC 变体）。
- **可整体剥离到 CPU**：概率建模与索引生成全是 tensor 运算（可 CPU 重算），压缩产物 = rANS 字节串。
- **关键取舍**：
  - 要与 RM **码流逐字节一致** ⇒ 必须复刻 compressai/ans 的 rANS 字节布局（唯一 C++ 依赖点）；
  - 只要**可编可解 + 真实字节数** ⇒ **任何自写算术/区间编码器都可替代** ⇒ 移植难度**大幅下降**（与本草案 §4 **R5**「板端为移植版、不宣称与 RM 一致」口径一致）。

### 8.5 量化敏感点（已确定，直接影响码率/可解性）

| 量 | 产出环节 | 后果 |
|---|---|---|
| **`mean`** | `Context/MCM` 输出 | `round(y − mean)` 的均值；误差 **>0.5 直接翻转符号**；且**编解码两侧须逐元素一致** |
| **`scale`** | `hyper_scale_decoder`（**整数定点**） | 直接决定 CDF 索引 ⇒ **码率** |
| **`medians`** | `EntropyBottleneck.quantiles` | `round(z − medians)` ⇒ `z` 的符号与码率 |

⇒ RKNN 量化噪声**破坏三者任一** ⇒ **码率跳变或解码失败**。这是 S1 对拍**必须锁住**的部分。

### 8.6 风险排序与结论

| 序 | 风险点 | 依据 | 判定 |
|---|---|---|---|
| 1 | **整数定点 `hyper_scale_decoder`**（int32 卷积 + 位右移 + per-channel shift） | `models/Fix_point_layer.py` `IntConv2d_sigma`；ONNX/RKNN 对 int32 位运算支持差、量化会破坏整数语义 | ⚠️ **最高**；退路 = 改浮点等价实现（需对拍） |
| 2 | **`Context/MCM` 的 reshape/split/stack 记忆序** | `src/codec/components/contexts/utils.py` `down_shuffle/up_shuffle` | ⚠️ 高 |
| 3 | **`PixelShuffle` / `ConvTranspose2d`** | `subpel_conv3x3` 等 | 中高 |
| 4 | **`replicate` Pad + `math.ceil` 尺寸**（`base_layers/utils.py`） | 导出前须固化 h/w | 中 |
| 5 | `where` / STE clamp、`erfc` 误入图 | `models/rec/common.py`、`entropy_models.py` | 低-中；裁剪务必剥离 |

**结论（分置信度）**：

| 命题 | 判定 | 置信度 |
|---|---|---|
| 单帧 DCM 的**神经网络部分**可拆成可导出子模块 | **很可能可行** | 中-高（算子面干净、无动态 shape；**未实测导出**） |
| **熵编码**可在板上 CPU 实现（**真码流**） | **可行** | 高（自写区间编码即可，不强求与 RM 一致） |
| **重建像素 + 检测框**可在板上呈现 | **可行** | 高（REC 为常规卷积；检测换板端轻量模型） |
| 端到端**单帧**板端跑通 | **有望**，但取决于 §8.6 序 1/2 的转换与对拍结果 | 中 |
| **实时**（连续帧） | **不在本方案目标内** | — |

> **⇒ 评估结论**：方案**值得做、且大概率能做**；但 **序 1（整数定点子树）与序 2（MCM 的 reshape 链）是真正的关口**。**在 §8.7 实测完成前，本评估不构成"能做"的承诺。**

### 8.11 **A-③ 实测：`context_mcm` 静态化（2026-10-10 已成）—— 关口 2 打通（导出层）**

- **脚本** = `DTM/code/s0d_context_static.py`；**产物** = `DTM/out_s0/07b_context_mcm_static.onnx` + `s0d_report.json`
- **根因**：`ContextUtils.down_shuffle / up_shuffle` 用 `y.numel() >> 1`、`k = m // W` 与 `shape` 派生做 reshape/split/stack ⇒ 导出成一大片动态形状算子，且 ORT 加载即报 **Type Error**；`Context.forward` 另有 `F.pad(..., w%2, h%2)` 与**全 1 掩码写 0** —— 后者在本尺寸下是**空操作**。
- **静态化做法**（固定 `B=1, C=128, H=36, W=60`，**不改算法语义**）：
  1. 所有 reshape/split 尺寸改用 **Python int 常量**（`m = B*C*H*W//2`、`k = m//W`），**不用** `numel()`/`shape()`；
  2. 去掉两处**空操作**（`pad(0)` 与全 1 掩码）；
  3. `quantize` 等价为 **`round(clamp(x, int32min, int32max))`**（STE 的 `detach` 在推理/导出下等价于 `round`）。
- **实测**：

| 对比 | max abs diff |
|---|---|
| PyTorch 原 `Context` **vs** PyTorch 静态化（`mu`） | **0.0** |
| PyTorch 原 `Context` **vs** 静态化（`y_rec`） | **0.0** |
| ONNX 静态化 **vs** 原 `Context`（`mu` / `y_rec`） | **7.2e-07** |

- **算子对比（大幅收敛）**：

| | 原导出 | 静态化后 |
|---|---|---|
| 动态形状类 | `Shape×51 / Gather×44 / Unsqueeze×182 / ConstantOfShape×12 / Expand×7 / Tile×7 / ReduceProd×6 / Cast×49` | `Shape×1 / Gather×1 / Unsqueeze×24 / ConstantOfShape×8 / Expand×8 / Tile×8`（**ReduceProd / Cast 清零**） |
| 计算类 | `Conv×33 / Relu×18 / Concat×79 / Reshape×59 / Slice×14 / Split×18` | `Conv×33 / Relu×18 / Concat×29 / Reshape×46 / Slice×10 / Split×15` |
| **ORT 加载** | ❌ **Type Error（模型非法）** | ✅ **可加载并推理** |

> **⇒ 关口 2 在"导出层"打通**：模型合法、数值与原实现一致（7e-7）。
> ⚠️ **残留少量动态形状算子**（`Shape×1 / Gather×1 / Unsqueeze×24 / ConstantOfShape×8 / Expand×8 / Tile×8`）——**是否被 `rknn-toolkit2` 接受 = S1 的判据，尚未测**。

| `07b_cum2` | 1.000 | ~1.0 | 0.992 / 0.985 | ❌ |
| `07b_cum3` | 1.103 | 1.02 | 0.984 | ❌ |

**(三) 推理链（根因）**

1. 4 个 phase 单独跑**全部 `corr = 1.000000`**、相对误差 ~5e-4（正常 FP16）⇒ **phase 网本身没问题**；
2. `round` 单测**零跳变** ⇒ `round` 算子本身也不发散；
3. 但 **`cum1` = "phase0 + round + 加法" 一跑就出 `max_abs = 恰好 1.000`** —— **±1 的整数级跳变**；连续的 FP16 误差只可能给 ~5e-4 量级，**不可能直接产生 1.0** ⇒ 只可能源自 **`round()` 在 .5 边界上的平局判定被 FP16 微小差推到另一侧**；
4. 发生率极低：**69120 个元素里 1 个（0.0014%）**，与 `mu` 越阈值点占比 **0.040%** 同量级 ✓ 自洽；
5. 该 ±1 误差经 `spatial` 拼接进入后续 stage，被卷积平滑后放大为 max 1.103 ⇒ **就是那条 0.04% 的长尾**。

**(四) 结论**

**根因 = FP16 精度下 `round()` 的固有平局效应（tie-breaking），单一机制**：
- **不可通过改图消除**（只能提高该处精度，FP16 NPU 无此选项）；
- **无害**：编解码两侧跑**同一张网 ⇒ 结果逐位一致 ⇒ 不会解码失败**；对码率影响 = **0.04% 符号翻转**。

⇒ **`07b` 判定从"降质待查"正式改为「可用」**。

1. **`07b` 的 2 输出在 RKNN 上退化为同一份** —— ORT 下 `y_rec`/`mu` 的 `maxdiff = 1.0`，但板上 `out0 == out1`（**逐位相等，都是 `mu`**）⇒ `y_rec` 输出丢失。⚠️ 因此 **§8.16(五) 与 S2/S3 用 `out_1` 当 `mu` 的对照，实际取到的仍是 `mu`**（本轮复核：`out_0`/`out_1` 对 `ref_mu` 均 corr **0.958498**、对 `ref_y_rec` 均 0.924839）⇒ **板端 `mu` 一直是对的**，该退化对本链路**无影响**；已另导单输出 `07e`/`07d` 规避（结果与用 `07b` **完全一致**）。
2. **FP16 误差被 MCM 内 8 级级联 `round()` 放大（真正的根因）** —— 把**与 PC 完全相同**的 `(y, psi)` 喂板上 `07e`：`mu` 仍差 **`mean|Δ| = 0.031`**、`|Δ| > 0.5` 占 **0.84%**、`|Δ| ≤ 0.01` 占 50.9%、**逐位相等 = 0%**（= FP16 噪声 everywhere + 平局翻转 few）。这是 §8.16 机制的**放大版**：§8.16 的 **0.04%** 是"同输入、单点"估计；**全链级联 8 次 `round` 后升到 ~1.3%**（1.27% 的 `y` 符号翻转与 0.84%~1.3% 同量级，自洽）。
3. **该误差经 `g_s → REC` 放大，但下游本身是干净的** —— 把**板端 `y_hat`** 喂回 **PC 的 FP32 下游**（08 → 09 → REC），**复现出同一张板端重建图**（`mean|Δ| = 0.035`、corr **0.999999**），且**同样复现对 RM 的 18.95 偏差** ⇒ **板上 08/09/10b 与熵编码数值都正确**，偏差**全部来自 `y_hat` 的误差**（REC 内部动态范围极大 ⇒ 对 `y_hat` 的微小差高度敏感；该敏感性在 FP32 下**同样存在**）。
4. ⇒ **结论**：**"跑通"成立**（真码流 + 真重建 + 板上 CPU 熵编码逐字节复现）；但**板上 FP16 移植版与 RM 的一致性有明显差距**（码率 **2.18×**、重建**可见偏差**），属 §4 **R5** 已登记的"**移植版 ≠ RM**"，并新增一条**机制性事实**：**MCM context 的 8 级级联 `round()` 对 FP16 误差高度敏感**（§8.16 的"无害"结论只对**单点同输入**成立，**不可外推到全链**）。

**(五) 一致性口径（已裁定）**

- ✅ **已裁定（用户 2026-10-10）= 接受**：接受板端 FP16 移植版的现测差距（码率 **2.18×** / 重建 `mean|Δpix| ≈ 18.95`）；**不设阈值**、**不采纳**「MCM context 改板端 CPU 跑 FP32」的备选（留档）；对外一律标注「**板端移植版**」（R5）。详见 §6 第 5 项。

### 8.22 方案 B 混合架构上板：检测器全链搬板 + 精度验证（S14，2026-10-13）

> **性质** = **板上实测（RK3588 NPU + CPU）+ 147 GPU 对照**。**非验收依据**（规则 `10-evidence.md` §1）。**不改 `main.py` / `config.yaml` / IQ、不停 `starlight-demo` 服务**，§13 全表不动、不放宽 §11.2、**不新增 / 不关闭 O 项**（登记 = 主基准 §15 **O166** 补记）。回写 = 主基准 §14 追加 31。

#### (一) 起点与约束

§8.21 证明精度可行（0.432 = 教师 91.9%），但 **RKNN rknnlite 2.3.2 对两阶段检测器零支持**（RoIHeads 拒转）⇒ R4 成为主阻塞。用户 2026-10-13 裁定：**全链路含检测器都要放在板上**。

**判别实验（先做，最便宜）**：X-101 的 `bottom_up` + FPN 是纯卷积，**与 RoIHeads 无关** ⇒ 单独导出转 RKNN 验证。结果：**转换成功、零不支持算子、板上 1.83 s/帧、p2~p6 shape 全对** ⇒ 方案 B（混合架构）生死闸门通过。

#### (二) 混合架构定型

```
NPU:  res2 → adapter → D → X-101 backbone+FPN → p2~p6      1.83 s  ✅
NPU:  RPN 头（conv 3×3 + obj/dlt 两个 1×1）                 0.85 s  ✅
CPU:  anchor 生成 + decode + NMS（纯 numpy）                0.10 s  ✅
CPU:  RoIAlign（纯 numpy，向量化）                          1.61 s  ✅
NPU:  box_head + predictor（Flatten + 4×Gemm）              0.65 s  ✅
CPU:  softmax + 按类别选 delta + box transform + NMS        0.01 s  ✅
─────────────────────────────────────────────────────────────────
检测小计                                                  5.04 s
+ HQ 增强 10 s + DCM 编解码 1.13 s  ⇒  全链预估 16.2 s（§6.2 预算 ≤45 s 内）
```

**关键设计**：`box_head` 无卷积（纯 FC：12544→1024→1024），1000 proposal 时约 116 GFLOPs ⇒ **必须上 NPU**（CPU 要 5~6 s）；只把 RoIAlign 与 FC 层留 CPU。

#### (三) 四项实现与逐层验证（全部与 detectron2 对齐后才上板）

| 项 | 产物 | 验证结论 |
|---|---|---|
| RPN 可转性 | `dcm_d/rpn/rpn_head.onnx`（2.27 MB） | 算子仅 **Conv×15 + Relu×5**；ONNX vs PyTorch `max\|Δ\|`=7.5e-07~4.3e-06；RKNN 5.4 MB 零告警；板上 p50 **644.80 ms** |
| anchor+decode+NMS | `dcm_d/rpn_np/rpn_np.py`（219 行，纯 numpy） | 5 张图 vs detectron2 **逐框一致**：框数 1000 vs 1000、IoU min≥0.999988、分数差 2.96e-08、anchor 逐元素差 0；29.47 ms |
| RoIAlign | `dcm_d/roialign_np/roialign_np.py`（195 行，纯 numpy） | **vs d2-CPU `max\|Δ\|` = 0（bit-exact）**；vs d2-GPU max\|Δ\|=3.06e-5~5.98e-5、corr=1.00000000（残差 = torchvision CUDA 内核 FMA 舍入）；向量化后 **615 ms/1000 proposals**（原 5257 ms，7.7×） |
| box_head+predictor | `dcm_d/boxhead/boxhead.onnx`（57 MB） | 算子 Flatten×1 + Gemm×4 + Relu×2；ONNX vs PyTorch cls 1.907e-06 / dlt 3.278e-07；RKNN 36.6 MB；板上 p50 **680.38 ms**；vs PyTorch cls 3.236e-03 / dlt 5.558e-04（FP16 精度内） |

**踩到并修掉的两个隐蔽坑**：
1. **rknnlite 会就地改写输入缓冲**（NCHW→NHWC）⇒ 喂给 RPN 的 backbone 输出被污染，RoIAlign 拿到错 shape（96 vs 192）⇒ 改喂 `p.copy()`。
2. **`bbox_pred` 输出是 (N, 320) = 80 类 × 4（类别相关框回归）**，不是 (N,4) ⇒ CPU 解码必须按预测类别选对应 4 个 delta。

**RoIAlign 口径与常见假设不同（运行时回读，已按实际实现）**：`output_size=(7,7)`、`scales=(1/4,1/8,1/16,1/32)`（**p2~p5 四级，不含 p6**）、**`sampling_ratio=0`（自适应网格 `ceil(roi_size/7)`，非固定 2）**、`pooler_type=ROIAlignV2`（**aligned=True**）。

### 8.23 MCM context 上板（方案 B）：码率与官方一致 + 全链预算落定（S15，2026-10-13）

#### (一) 起点：1344 重导后暴露的 RKNN 缺陷

#### (二) 根因定位（逐层二分，非猜测）

板上 vs 147-FP32 逐层比对，**发散精确起始于 `mu`（07e 输出）**：

| f0 / y / z | 0.0013 / 0.0043 / 0.0032 | **1.000000** | 0% |
| z_hat | 1.0000 | 0.999304 | 0.31% |
| psi | 0.0934 | 0.998775 | 0% |
| scale | 143.4 | 0.999369 | 69.99% |
| **mu（07e）** | **2.0122** | **0.711809** | **50.11%** |
| y_hat | 3.4436 | 0.780719 | 82.00% |
| res2 | 1.1964 | 0.878755 | 0.91% |

**三组对照判定「RKNN 是主因、非 FP16」**：

| 对照 | mu corr | mu \|Δ\|>0.5 | res2 corr |
|---|---|---|---|

4 种导出格式并存：YOLO（`labels/*.txt` + `train.txt` + `data.yaml`）、COCO 1.0、CVAT XML 1.1、Pascal VOC 1.1，另有 `meta/{dataset_stats,cvat_labels_40}.json`。**原状** = **137 图 / 83 有标注 / 54 空图 / 177 框**，标签空间 **40 类**（实际用到 11 类）。图像为 **HQ E 臂增强后的 960×540 PNG**（`*_hqE.png`）⇒ **与部署 DCM 检测的输入域同源** ✓。

#### (三) 关键发现 ①：类别索引与部署检测器**不兼容**

包内是 **40 类子集、重新编号 0..39**（COCO json 里 1..40），而部署检测器 = **COCO-80**（`faster_rcnn_X_101_32x8d_FPN_3x`），且训练脚本 **硬断言 80 类**（`b2c_finetune.py` L201）。11 个使用类中 **10 个索引错位**，只有 `person` 恰好一致：

| person | 0 | 0 ✓ | bottle | 13 | 39 |
| backpack | 7 | 24 | cup | 15 | 41 |
| umbrella | 8 | 25 | dining table | 26 | 60 |
| handbag | 9 | 26 | tv | 27 | 62 |

⇒ **必须按"类名"重映射**，按数字搬会静默训错。**同类风险**：本包 COCO json 的 `category_id` 与官方 COCO 的 id（1..90 带空洞）也不一致。

#### (四) 关键发现 ②：**跨批次重复 ⇒ 去重后 137→79**（并订正 §8.30）

全量 md5 比对：`images/` **137 文件仅 79 唯一**（58 重复）；`dark_src/`、`hq_e_out/` 同样 79 唯一 ⇒ 重复源自**拷贝环节**。重复全为**跨批次同号重拷**（4 类：`hq60_261002c_XX↔u4b_261002_XX`、`hq60_261002b_XX↔u3_38_261002_XX`、`pub17_261002c_XX↔u4b_261002_XX`、`pub17_261002b_XX↔u3_38_261002_XX`）。

**⚠️ 订正 §8.30**：其去重工具 `dedup_same_scene.py` 的判据含"**同 scene（批次前缀）**"⇒ **只在同批次内比较**，跨批次重复根本不在比较范围内 ⇒ §8.30 的「**137 → 137，0 去重**」与「这 5 批是一场景一图离散采集」**均为误判**，**该结论作废**（前提变更 = 由"同批次内判重"改为"全量 md5 跨批次判重"）。

**去重执行**（用户裁定「保留一份·批次优先级」）：规则 = 每组按 `hq60 > pub17 > u4b > u3_38` 保留一份；**若高优先那张无标注而低优先的有，则保留有标注的那张**（否则丢标注）。58 个重复组中：**6 组双方框数不同** / 28 组仅坐标抖动 / 24 组只有一方有标注。重复件移入 `images/_dup/`、`labels/_dup/`（**可回退**），并产出 `dedup_report.json`。

#### (八) 域内微调（S20-A，用户批准「方案 A＝干净留出」）

- **划分**：留出 = `260929` 采集日全组（**13 图 / 24 框 / 8 类**）；训练 = 其余 **66 图 / 81 框**（含 27 张空图作负样本）。**训练用过的图不再作验证集**（用户明示）。

**④ 关键结论（含对本草案前一轮判断的订正）**

1. **微调方向有效**：两组均显著高于微调前 0.0836（+42% ~ +62%）。
2. **⚠️ 订正（2026-10-16）**：本轮之前曾据"同轮内 `ep60 0.1354` vs `ep60_ema 0.1027`"判断「**EMA 有害**」⇒ **该判断不成立**。无 EMA 重跑的 ep60 = **0.1053**，而有 EMA 那轮的同为 ep60 **主权重** = **0.1354**；两轮 `loss_cls` **自 ep20 即分岔**（0.0761 vs 0.0731）⇒ **EMA 开关本身改变整条训练轨迹**（消耗 RNG）。**依据变更** = 由"同轮内 EMA 权重 vs 主权重"改为"开关级跨轮对照"⇒ **不能据此判定 EMA 优劣**。
3. **根因 = 留出集太小**：13 图 / 24 框下，**单次运行的波动（±0.03 mAP ≈ ±30%）已大于组间差异** ⇒ 该留出集**分辨不了** EMA / 最优轮数这类量级的差异。**要定论只能多 seed 重复或换留出交叉验证**（本轮未做）。

#### (九) 结论与未决

- **可主张**：① 标注可用（重映射后）、② 旧权重在该域内**全面弱于**新权重（尤其召回）、③ 用该数据微调**方向有效**（留出 mAP 约 0.084 → 0.11~0.14）。
- **不可主张**：EMA 取舍、最优轮数、提升幅度的准确值（受留出集大小限制）。
- **未决（留待用户裁定）**：**40 类 vs 80 类头**。用户 2026-10-16 明示「这 40 种分类是我想要的」，但**未裁定实现路线**：**A** = 保持 80 类头 + 按名映射（板端 RKNN **零重导**，但另 40 类仍可能被检出）；**B** = 真改 40 类头（`NUM_CLASSES=40` → 重训 → **重导 RKNN** → **重测 §6 耗时** → 重定 `DROP_CLASSES`）。折中 **C** = A + 运行期"只保留 40 类"白名单（板端零重导即得 B 的主要收益）。

**S13（§8.21）后的判断（2026-10-12）**：
- **精度基准可行性 = 已求证**。教师（主流顶配 X-101-FPN 3x，公布 43.0）在 500 张 COCO 上 **0.470**；官方 DCM q31 特征域 **0.300**；**根因 = 特征域范式未适配 off-the-shelf 检测器，非编码损失**（恒等对照 0.136 为证）；插入可训练 D 模块微调后 **0.432**（教师 91.9%，判据 >0.40 通过）⇒ **「DCM 取特征 + 检测」在精度上具备演示可行性**。
- **但落地形态必须重新设计**：0.432 依赖 GPU + detectron2 两阶段检测器（401 MB 权重），**RKNN 对两阶段检测器零支持**；且 COCO 正常光域 ≠ 暗箱 IMX415 域。**这两个缺口不取决于精度，加训练量无用于此**。
- **下一步 = 按 §8.21(七) 的教训重新设计开发方案**（目标：高精度 + 可上板），**而非继续在既有自移植学生头（§8.20 B 阶段）上加码率或加训练量**。

**风险提示（如实）**：**R1（算子可转换性）已消除**（S0~S9 全过）；**R2/R3 已按 FP16 + rANS 落定**（一致性口径 = 接受）；**R4（检测器）已变形** —— 原 VOC-20 上板验证虽过，但 §8.21 证明其特征域精度上限仅 0.30、且当前高精度方案（X-101-FPN + D）**无法上板** ⇒ **R4 未解除，反而成为主阻塞**（**⚠️ 该判断已被 §8.22 S14 推翻**：X-101 `bottom_up`+FPN 可独立转 RKNN（零不支持算子）⇒ **混合架构定型、检测器全链搬板**，R4 主阻塞**已解除**；见主基准 §14 追加 31）；**R5（移植版 ≠ RM）的如实标注义务长期有效**；**R6（新增）= 域差距未验**（COCO 跨域外推，非演示帧实测）。
