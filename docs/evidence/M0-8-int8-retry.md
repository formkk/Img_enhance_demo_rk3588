## 1. 目的

三档耗时实测（`docs/evidence/M0-2-ab-toolkit-version.md` §5.2）显示 480×272 曲线估计需 **70.9 ms**（FP16 / core0），与主基准 §7.1 的预算相差约 7 倍（已登记 **O28**）。故探索两条提速路径：

1. **量化**：INT8 是否能显著提速，且曲线场是否仍可用（M0-8 本体）；
2. **执行单元**：把这 10K 参数的小模型放到 **CPU**（A76/A55）上是否比 NPU 更快（若成立，可释放 NPU core0，但会触及 §4.1 / §6.1 的绑核契约，须走裁定）。

## 2. 方法

| 项 | 设置 |
|---|---|
| 模型 | `models/zde/zde_curve_480x272.onnx`（官方 Zero-DCE++ 曲线估计器，opset 12，与 A/B 同源） |
| PC 工具链 | `rknn-toolkit2 **2.3.2**`（v3.22 定版，conda `rknn232`） |

| 校准集 | **LOLv2 `Real_captured/Train/Low` 均匀抽 50 张** → resize 480×272 → RGB PNG（**代用数据**，O7；非本项目实拍域） |
| 板端运行时 | `librknnrt 2.3.2`（隔离方式见 A/B 证据 §5.2） |

| CPU 对照 | ONNX Runtime 1.19.2（板上 pip `--target` 安装），`intra_op` 1 / 4 线程，输入 NCHW、÷255 |

## 3. 结果

### 3.1 FP16 vs INT8（同一 ONNX、同一 shape、同一板）

| 指标 | FP16（基线） | **INT8** | 变化 |
|---|---|---|---|
| 编译告警 | 0 | **0** | — |
| Total Internal Memory | 61,965 KB | **24,480 KB** | **−61%** |
| Total Weight Memory | 24.25 KB | **18 KB** | −26% |
| `.rknn` 大小 | 1,908,277 B | **803,023 B** | −58% |
| 曲线场范围 | −0.35229 ~ −0.05759 | **−0.3536 ~ −0.0638** | **同量级，无塌缩** |
| 曲线场均值 | −0.3123 | −0.3166 | 同量级 |
| **板端 vs PT 对齐（max abs）** | **4.91e-4** | **1.72e-2** | **退化 35×** |
| 推理中位（30 次） | 70.9 ms | **59.0 ms** | **仅 −17%** |
| min / p90 | 65.2 / 100.4 ms | 54.0 / 69.4 ms | — |

**判定**：

1. **"INT8 塌缩"在本板 + 本工具链 + 本校准集下未复现**——曲线场范围与 FP16 同量级，可直接用于 8 次迭代增强。⚠️ 但这**不等于**精度闸口通过：对齐退化到 **1.72e-2**（FP16 为 4.91e-4），须按 O23 的量化误差闸口（图像域指标）另行判定，且校准集必须换成**实拍域**（M1）。
2. **INT8 不是提速主力**：内部内存降 61%、模型小 58%，但耗时只降 **17%** ⇒ 瓶颈既**不是单纯算力**（INT8 的 MAC 率翻倍却只快 17%）也**不是单纯带宽**（内部内存降 61% 亦只快 17%），更符合**每层/每任务的固定开销 + 小通道 depthwise 的低流水利用率**——三档拟合出的约 **13 ms 固定项**即其佐证（§3.3）。

### 3.2 执行单元对照：CPU 路线（实测否决）

| 路径 | 480×272 曲线估计中位 | 输出与 PT 一致性 |
|---|---|---|
| **NPU core0（FP16）** | **70.9 ms** | 对齐 4.91e-4 |
| NPU core0（INT8） | 59.0 ms | 对齐 1.72e-2 |
| **CPU（ONNX Runtime，4 线程）** | **124.4 ms** | **输出范围与 PT 完全一致**（−0.352239 / −0.057606） |
| **CPU（ONNX Runtime，1 线程）** | **631.7 ms** | 同上 |

**判定**：CPU 比 NPU **慢 1.8~8.9 倍** ⇒ **不采用 CPU 路线**，§4.1 / §6.1 的"曲线估计绑 NPU core0"维持不变（本条为先导实测，正式结论仍可在 M0-2 复测后登记）。

### 3.3 耗时构成的量级说明（用于决定后续优化方向）

- 该模型在 480×272 的实际计算量，按逐层核算约 **1.3 G MACs**（≈2.6 GFLOPs）：其中 **1×1 pointwise 卷积约占 75%**（conv2~conv6 各 1.3~2.7 亿 MACs），3×3 depthwise 约占 25%。
  ⚠️ **口径提示**：§4.1 引用的"0.115 GFLOPs @1200×900"（历史值）与上述逐层核算相差约 **190 倍**（二者不可能同时成立），故本档**不以该历史值为依据**，只用逐层核算 + 实测耗时；若后续要以 FLOPs 口径讨论预算，须先在 §15 登记并回写 §4.1。
- 三档实测近似线性（§5.2）：`耗时 ≈ 13 ms（固定）+ 0.407 µs/像素`。故：
  - 换算 NPU 有效算力 ≈ **37 GFLOP/s**（≈ 6 TOPS 的 0.6%），说明**小通道 + depthwise 导致 MAC 效率极低**，不是"NPU 不够快"；
  - **最有效的杠杆是降低估计分辨率**（256×144 = 27.7 ms，−61%），其次是**降低估计频率**（5~15 Hz 可配，见 §3.4），而不是换精度。

### 3.4 频率与占空比（O28 的量化依据）

| 档位 | 单次耗时 | @5 Hz | @10 Hz | @15 Hz |
|---|---|---|---|---|
| 256×144 | 27.7 ms | 14% | 28% | 42% |
| 480×272（默认档） | 70.9 ms | 35% | 71% | **106%（不可行）** |
| 960×544 | 225.2 ms | 113%（不可行） | — | — |

⇒ **默认档 480×272 时 §4.3 的"5~15 Hz"上限不可达**（上限 ≈14 Hz，且无余量给同核并发）；这正是 **O28** 的裁定内容。

## 4. 未做（后续）

2. **逐层精度分析**（`rknn.accuracy_analysis`）与 **图像域指标**（8 次迭代后的增强图 PSNR / 最大像素差）；
3. **实拍校准集**（M1，IMX415 暗房/夜景/人脸）替换代用集后复检；
4. **C-API 计时**（排除 python/lite2 层开销；本轮 3 档线性性表明该开销小于数 ms）；
5. **更低档位**（如 240×136，均为 8 的倍数）的可行性与画质 A/B（属 §4.3 的档位表变更，须走 O7/O23 流程）。

## 7. 【更正】C-API 剖析（2026-09-17 19:2x–19:3x，**推翻 §3.1 的"INT8 只快 17%"**）

§3.1 的结论建立在 `rknnlite`（python）路径上，而该路径自带 **~20–26 ms 的固定 IO 开销**，把 INT8 的收益掩盖了。改用 `RKNPU2 C API`（新脚本 `tools/rknn_c_probe.c`，含逐层剖析 `RKNN_QUERY_PERF_DETAIL` / `RKNN_QUERY_PERF_RUN`）后，结论改变。

### 7.1 配置矩阵（480×272，core0，30 次；取 min 为最干净的信号，median 受板上 CPU 抖动影响）

| 模型 | 输入类型 | 输出转 float | wall min | **NPU run min** | wall − run |
|---|---|---|---|---|---|
| FP16 | float32 | 是 | 75.4 ms | 49.3 ms | 26.1 ms |
| FP16 | float32 | 否 | 73.7–100.0 ms | 48.9–77.8 ms | 19.5–72 ms（抖动大） |
| FP16 | **uint8** | 否 | 70.9 ms | 49.5 ms | **21.4 ms** |
| **INT8** | **uint8** | **否** | **33.0 ms** | **31.7 ms** | **1.4 ms** |
| INT8 | uint8 | 是 | 40.9 ms | 33.7 ms | 7.2 ms |

**判定（更正 §3.1 第 2 条）**：
- **INT8 是有效的主力杠杆**：wall 从 **70.9 ms → 33.0 ms（2.15×）**，NPU 自身 49.5 → 31.7 ms（1.56×）；内部内存 63.5 → 25.1 MB。
- 另一半天在 **IO 路径**：FP16 模型上 `wall − run` 恒有 **~21 ms**（uint8 也压不掉），而 **INT8 模型仅 1.4 ms**——说明该缺口与 FP16 模型的输入/输出转换路径绑定；**"喂 uint8 + 不要求 float 输出"对 INT8 模型近乎免费**。
- 因此运行时必须走 **C API（或等价零拷贝）路径并喂 uint8**；§3.1 中基于 python 路径的耗时（59/70.9 ms）**仅作 python 原型参考，不得作为预算依据**。
- 精度闸口仍未过（对齐 1.72e-2，见 §3.1），INT8 进入主线仍须 O23 的图像域判定。

### 7.2 逐层剖析（FP16，480×272）：**memory-bound + 每层固定开销**

`RKNN_QUERY_PERF_DETAIL` 摘录（Time µs / MacUsage）：

| 层 | 算子 | Time | MacUsage | RW(KB) |
|---|---|---|---|---|
| 1 | InputOperator（CPU） | 34 | — | 0 |
| 2 | Conv 3ch | 1631 | **0.14%** | 765 |
| 3 | Conv(dw) 3ch | 2750 | **0.25%** | 2040 |
| 4 | ConvRelu(pw 3→32) | 2257 | 1.08% | 2040 |
| 5 | Conv(dw) 32ch | 3775 | 1.95% | 8160 |
| 6 | ConvRelu(pw 32→32) | 3163 | **8.26%** | 8162 |
| 7–10 | dw32 / pw32 / dw32 / pw32 | 3932 / 3203 / 3944 / 3138 | 1.9% / 8.2% | 8160 / 8162 |

- **MacUsage 最高仅 8.3%**：NPU 的 MAC 阵列 ≥92% 时间在等数据 ⇒ **纯 memory-bound**，不是算力不足。
- 拟合 `单层耗时 ≈ 1.4 ms + 0.28 ms/MB`（三点拟合，含 3 通道 head 层），19 层 ⇒ **固定项约 27 ms**（FP16）；这也解释了为什么"INT8 使内存降 2.5× 只换来 1.56×"。
- 每层 RW 恰为一张全张量（8.16 MB @32ch），说明**中间结果全部落 DDR 再读回**；本板 `RKNN_QUERY_MEM_SIZE` 报 `sram=0/sram_free=0`（内核未为 RKNN 保留 SRAM），且单张中间张量 8 MB ≫ 任何片上容量 ⇒ **`RKNN_FLAG_ENABLE_SRAM` 在本板无效**（实测亦无变化）。

### 7.3 追加约束（实现时必须遵守）

1. **配了 mean/std 归一化的模型只接受 NHWC 输入**：传 NCHW 时运行时报
   `Meet unsupported src layout for normalize: NCHW, only support NHWC src layout!`（`rknn_inputs_set` 返回错误）。
   ⇒ RGA → NPU 的喂入必须按 NHWC uint8。
2. `rknn_run` 的 `run_duration` **包含**输入归一化段（同一 FP16 模型：float32 输入时 run min 77.8 ms，uint8 输入时 49.5 ms）。
3. 逐层剖析需 `rknn_init(..., RKNN_FLAG_COLLECT_PERF_MASK)`；本探针用的头文件取自归档内 `rknpu2_runtime_2026_7_31`（2.4.2a12 配套，与 2.3.2 运行时的上述查询接口兼容；**头文件版本差异需在 M0-2 正式登记时复核**）。

### 7.4 对"480×272 ≤30 ms"的可行路径（按收益/成本排序）

| 措施 | 预期（wall） | 依据 / 代价 |
|---|---|---|
| ① **INT8 + uint8 + 不转 float（C API）** | **33 ms** | **已实测**；代价 = O23 量化误差闸口 + 校准集换实拍域 |
| ② 估计分辨率降到 256×144（曲线场照旧上采样到 1080×608） | **≈12–15 ms** | 256×144 像素为 1/3.54、INT8 固定项不变；属 §4.3 档位与 O7/M0-3 A/B |
| ③ 模型减宽（number_f 32→16） | ≈20 ms @480×272 | 逐层 RW 减半（pointwise MACs ∝ nf²），**需微调**（配方见 `environment/pre-research-inventory.md` §3） |
| ④ 双核空间切分（240×272 两半 + 3×3 halo） | ≈23 ms | 只砍数据项、砍不掉每层固定项；且与 HQ 的 core1+2 契约冲突，须走 §15 裁定 + M0-6 并发验证 |
| ⑤ depthwise+pointwise 合并为单 3×3 dense conv | 不确定（省 ~5 ms 固定项，MACs ×7） | 层数 14→7，但 MacUsage 会上升；须实测 |

⇒ **推荐组合：① + ②**（INT8 + 256×144 估计），可达 **12–15 ms 级**，且都不需要改模型或改分核契约；若必须保持 480×272 估计，则 ①（33 ms）已近目标，再要 ≤30 ms 需 ③ 微调。

## 8. 【达标】多 context 空间切分并行：480×272 曲线估计降到 **20.3 ms**

**动机**：§7.2 的逐层剖析表明单核下 19 层几乎全是 memory-bound + 每层固定开销，单核墙 ≈31 ms（INT8）。RK3588 有 3 个 NPU 核，故改为**按空间切条带、各条带独立 context 绑不同核并行**。

**实现**：新增 `tools/rknn_split_probe.c`（pthread + 多 context + `rknn_set_core_mask`）。感受野半径 = 7 px（7 次 3×3），故条带间需 **7 px 真实数据 halo**；切片模型输入固定 **272×256**（条带宽 240 + 2×7 halo 取整）。

### 8.1 实测（480×272 整帧，INT8，切片模型 `zde_curve_256x272_int8_tk232.rknn`）

| 配置 | 整帧耗时（40 次） | 说明 |
|---|---|---|
| 单核串行（core0，480×272 单模型） | 30.9 / **34.5 ms**（min/中位） | §7.1 基线 |
| **2 条带并行（core0+core1）** | **19.9 / 20.3 ms** | **达标（<30 ms）** |
| 2 条带同核对照（core0+core0） | 32.0 / 38.1 ms | 证明增益来自**真并行**而非切分本身 |
| FP16 2 条带并行（备选路径） | 31.5 / 32.7 ms | 略超 30 ms；若 INT8 精度闸口不通过，需 3 核/3 条带 |

### 8.2 等价性验证（**必须做**，否则切分不可用）

| 对照 | 均匀灰帧 | 真实暗帧 |
|---|---|---|
| 整帧输出 vs 切分拼接（max abs） | **5.55e-3** | **1.53e-2** |
| 同对照的内部/接缝/边缘分区 | 均为 4~6e-3 | 边缘 0.007~0.012、接缝 0.007~0.011 |

切分后的差异**已回到 INT8 自身噪声量级**（单模型 vs PT = 1.72e-2），且**边缘与接缝与内部同量级** ⇒ **切分未引入额外误差**。

### 8.3 实现陷阱（**务必记录**）：INT8 非对称量化下不能靠"注入边框零"补边

首版实现让每条带缓冲区**向帧外扩 7 px 并填 0**，结果帧最外 5~6 列出现 **0.05~0.11** 的假偏差（接缝处却完全正常，故极易误判为滤波器/几何问题）。

- **根因**：INT8 输入是**非对称仿射量化**（zero_point ≠ 0），uint8 的 `0` 反量化后**不等于实值 0**；而模型自身的 conv padding 用的是"正确的实值零"。两者不一致 ⇒ 只在**帧最外沿**产生偏差（衰减半径 = 感受野 7 px）。
- **正确做法**：**条带缓冲区与帧边界齐平**（首条带左边 = 帧左边界、末条带右边 = 帧右边界），帧外一律交给模型自身的 padding；**只有条带之间的内部边界才需要真实 halo**。修正后偏差降至 5.6e-3/1.5e-2（§8.2）。
- 同一陷阱对**其他"手工补边"场景同样成立**（如 §3.1 的 RGA 零填充策略）：**补边值必须在量化域语义上等于实值零**，否则边缘行会漂移。

### 8.4 结论与待裁定项

1. **480×272 曲线估计 ≤30 ms 已达成**（INT8 + 2 条带 = **20.3 ms 中位**）⇒ **不需要为降耗时把估计档降到 256×144**（该档位仍可作为画质/跟手性的可选档，由 M0-3 的 A/B 决定）。
2. 实现约束：曲线估计须走 **INT8 + uint8 喂入 + C API**，且**多核空间切分**（2 条带、core0+core1）。
3. **与 §8.1 分核契约冲突**（原定"core0 = 实时、core1+2 = HQ"）⇒ 已登记 **O29** 待裁定：可选方案 = (a) 估计用 core0+core1、HQ 触发期间估计退化为单核；(b) 估计用 core0+core2、HQ 用 core1；(c) 改 3 核分时（HQ 期间暂停估计，§8.2 式降级）。须在 M0-6 并发压测中验证"HQ 期间 MIPI 掉帧 ≤20%"。
4. 未做：3 条带（需 176×272 切片模型，且 3 核全占用）；zero-copy 预分配 IO（当前 IO 开销仅 3.9 ms）；FP16 路线下的 ≤30 ms（需 3 条带）。

## 9. 图像域精度闸口（INT8 → 主流线的判据；M0-8 定稿依据）

**方法**：新增 `tools/enhance_ref.py`（官方 8 次迭代曲线应用的**参考实现**：`y ← y + x_r·(y² − y)` ×8，末端裁剪；见主基准 §3.3）。对同一帧（`input_480x272.npy`，真实暗场景）分别用 **PyTorch 真值曲线场**与**板上各候选曲线场**做增强，比较**图像域**结果。
报告：`docs/evidence/reports/M0-2/int8_image_gate.json`；曲线场落档 `docs/evidence/reports/M0-2/curve_board_{fp16,int8,int8_split2}_480x272.npy`。

### 9.1 结果（480×272，代用数据）

| 候选 | 曲线场 max abs（vs PT） | **增强图 PSNR（vs PT 增强图）** | 最大像素差 | 平均像素差 | >1 LSB 占比 | >2 LSB 占比 |
|---|---|---|---|---|---|---|
| **FP16 单模型** | 4.91e-4 | **76.98 dB** | **0.20 LSB** | 0.024 LSB | 0 | 0 |
| **INT8 单模型** | 1.72e-2 | **51.07 dB** | 7.46 LSB | 0.51 LSB | 14.8% | 1.56% |
| **INT8 双条带拼接**（交付路径） | 1.96e-2 | **53.46 dB** | 9.60 LSB | 0.35 LSB | 8.1% | 0.67% |

### 9.2 判定

1. **FP16 = 图像域 bit 级不可分**（76.98 dB，无一个像素差 ≥1 LSB）⇒ 精度上完全安全。
2. **INT8 = 高保真但非 bit 透明**（51~53 dB；最大 7.5~9.6 LSB 出现在少数像素，>2 LSB 者占 0.7~1.6%）。51 dB 远高于"肉眼可辨"的常见门槛（~40 dB），但在**平坦暗区**存在轻微带状差异的理论风险。
3. **切分路径不额外劣化**：拼接结果 53.46 dB 与单模型 51.07 dB 同档（差异主要来自各自的 INT8 量化噪声）⇒ **双条带方案可安全叠加**（§8 已验零额外误差）。
4. **O23 的 U8 闸口 ≠ 本闸口**：O23 判的是**曲线场表示精度（U8 vs FP16 场）**，其判据为"以同档 FP16 场为参考 + 逐像素 diff + **盲评（≥2 人）**"；本节判的是**模型量化（INT8 vs FP16）**。两者独立，**不可互相替代**。
5. **进主线的剩余条件（未完成）**：① O23 式的**盲评 ≥2 人**（需真人）；② **M1 实拍校准集**重转 INT8 后复检（现为 LOLv2 代用集，`provisional`）；③ 因双条带已留出约 **10 ms 余量**（20.3 vs 30 ms 目标），**优先尝试混合量化**（`e_conv7`+`tanh` 输出层留 FP16），预期把曲线场误差降到 ~1e-3 量级（图像的 ≥65 dB），代价是辨识可接受的速度回退。
